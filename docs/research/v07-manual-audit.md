# v0.7 입안 자료 재점검과 후속 기획

검토일: 2026-10-26  
범위: 사용자가 제공한 입안 자료 5종, 추가 출처 안내문, 현재 저장소의 검색·검토·입안·문서 생성 코드  
자료 버전: `moleg-2026-10-24-v1`

## 1. 결론

**핵심 자료 5종은 모두 들어 있다. 가장 큰 보완점은 자료를 더 넣는 일이 아니라, 자료의 판단 순서를 실제 작성 과정과 문서 항목에 연결하는 일이다.** 현재 앱은 자료 검색, 원문 다운로드, 쪽수 있는 AI 검토, 개정안·대비표 생성, 내부 인용 정정, 선택한 검토안 반영까지 갖췄다. 다만 법제 담당자가 고민하는 위임 범위, 기존 신청·계약의 처리, 전부개정·폐지, 의견제시 요청서 완성은 아직 질문·메모 또는 일반 AI 설명에 의존하는 부분이 크다.

이번 검토에서 우선순위가 높은 다섯 과제는 다음과 같다.

1. 조문마다 **무엇을 할 권한인지, 어떤 근거가 있는지** 연결하는 근거표.
2. 개정 조문마다 **기존 대상자와 진행 중인 업무를 어떻게 처리할지** 묻는 부칙 작성 지원.
3. 제정·일부개정과 구분되는 **전부개정·폐지 전용 산출물**.
4. 공식 요청서의 항목을 채워 내려받는 **의견제시 요청서 작성 기능**.
5. 여러 규정과 별표·서식을 함께 살펴보는 **변경 영향 관리**.

이 문서는 업로드 자료를 바탕으로 한 제품 점검이다. 각 매뉴얼의 판본·수록 시점과 개별 법령의 현재 효력은 구분한다. 특정 실제 조례의 적법성이나 2026-10-26 현재 법령 내용에 대한 판단은 하지 않았다.

### RAG에 대한 정확한 설명

현재 방식은 단어·한글 부분 문자열·동의어를 결합한 검색이다. 모델 자체를 재학습시킨 방식이 아니며, 임베딩 데이터베이스가 없다는 이유로 기능이 빠졌다고 볼 수 없다. 원문 파일과 검색 자료를 앱에 배포하고, 질문에 관련된 발췌문을 모델에 제공한다. 모델을 바꾸어도 자료·검색·출처 검증을 계속 사용할 수 있는 구조는 확산 가능성의 강점이다.

`/api/knowledge/assist`는 검색 결과 최대 6개, 원문 발췌 총 5,500자를 제공한다. 긴 본문 전체를 모든 관점에서 검토한다는 보장은 없다. 현재 검색어에는 질문과 본문 앞 700자가 사용된다. 복합 질문은 ‘위임’, ‘부칙’, ‘문장 정비’처럼 쟁점을 나누어 검색하고, 답변에 **검토한 조문 범위와 확인하지 못한 쟁점**을 보여 주는 개선이 적합하다. 인용문이 실제 원문에 있다는 검사는 이미 있지만, 인용이 있다는 사실만으로 해당 사안에 맞는 법적 결론이 증명되는 것은 아니다.

구현 근거: `src/server/knowledge.ts`, `src/server/knowledge-answer.ts`, `src/app/api/knowledge/assist/route.ts`, `docs/RAG-ARCHITECTURE.md`.

## 4. 우선순위별 개선 기획

### P0-1. 조문별 근거표: 조목이가 첫 세 가지 질문을 안내

첫 화면에서 다음을 묻는다. ‘누구에게 적용하나요?’, ‘새 의무·신청·허가·제재가 있나요?’, ‘그 내용을 정하도록 한 조문이 있나요?’ 답변은 각 조문에 연결하고, 근거가 없거나 범위가 불명확한 부분만 추가 확인으로 올린다.

최소 데이터는 대상 조문, 사무 성격, 입안 주체, 위임 조문 원문, 위임 대상·범위, 새로 정하는 사항, 근거 확인 상태다. 법령 이름을 썼다는 이유로 위임이 확인됐다고 표시하지 않는다. 포괄 위임, 재위임, 권한 위임은 구분해서 검토하며, 모든 조례에 개별 위임이 필요하다고 오해시키지 않는다.

**자료 근거:** 길라잡이 PDF 21–26쪽/본문 13–18쪽의 규정 형식·재위임 설명, PDF 68쪽/본문 60쪽의 권리 제한·의무 부과, PDF 75쪽/본문 67쪽의 위임 관련 유의사항. 현재 `src/engine/lint.ts`의 `근거-01`은 조례의 과태료·벌금·징역·과징금 키워드와 법령명 표기를 보는 제한된 탐지다. 허가·등록·신고·새 의무 전체를 구조적으로 검증하는 기능은 아니다.

**완료 기준:** 상위법 원문이 없는 사례는 미확인으로 남고, 동일 법령을 인용했어도 다른 대상·범위인 사례를 통과로 표시하지 않는다. 권리 제한이 없는 자치사무 사례에는 불필요한 위임 부족 경고를 남발하지 않는다. 법제 담당자가 확정한 사례로 오탐과 누락을 함께 측정한다.

### P0-2. 부칙을 ‘문장 한 칸’에서 ‘기존 업무 처리표’로 확장

조문이 바뀌면 ‘이미 접수한 신청’, ‘진행 중인 계약·위탁’, ‘기존 위원 임기’, ‘이미 발생한 위반행위’, ‘준비가 필요한 서식·시스템’ 중 관련되는 것만 보여 준다. 각 항목은 기존 대상, 기준 사건·날짜, 종전/개정 규정의 적용, 확인해야 할 개별 근거를 기록한다. 그 결과로 적용례·경과조치·특례 초안을 각각 생성한다.

**자료 근거:** 길라잡이 PDF 343–344쪽/본문 335–336쪽의 부칙 구성, PDF 349쪽/본문 341쪽의 시행 준비, PDF 362–363쪽/본문 354–355쪽의 적용 관계, PDF 376쪽/본문 368쪽의 특례. 자료는 변경 내용마다 적용 관계를 살피도록 안내한다. ‘기존 대상은 무조건 종전 규정’ 또는 ‘개정 규정은 모두 소급 적용’처럼 하나의 답으로 처리하면 안 된다.

현재 `AddendaSpec`은 시행일, 경과조치 문자열, 재검토기한 여부만 담고 `DocsTab`도 이에 맞는 입력을 제공한다. 일반 점검표에는 종전 관계와 새 규정 적용 검토가 있으나 대상별 판단을 저장하는 구조는 없다.

**완료 기준:** 사용자 입력 없이 과거 사건 처리 결론을 채우지 않는다. 서로 다른 시행일, 새 신청에 대한 적용례, 기존 임기 경과조치가 함께 있어도 문서가 각각의 조문과 연결되어 나온다. 본문이 바뀌면 관련 부칙 판단을 다시 확인하도록 표시한다.

### P1-1. 전부개정·폐지를 별도 작업으로 지원

현재 `Project.mode`는 `enact | amend`이고, `src/lib/docs.ts` 개정 문서 제목은 ‘일부개정’으로 생성된다. 개별 조문 전체를 바꾸는 작업과 자치법규 전부개정은 구분해야 한다.

입안 목적과 변화 범위를 보고 제정·일부개정·전부개정·폐지를 추천하되 사용자가 판단 근거를 보고 결정하게 한다. 분량 비율만으로 전부개정을 확정하지 않는다. 종전 부칙의 적용례·특례·경과조치가 계속 필요한지도 함께 묻는다. 문서 제목, 개정 지시문, 본칙·부칙 구성과 첨부 문서가 방식에 맞게 달라져야 한다.

**자료 근거:** 길라잡이 PDF 421–422쪽/본문 413–414쪽의 개정 방식 선택과 예외, PDF 457–458쪽/본문 449–450쪽의 전부개정·제정 형식, PDF 390–391쪽/본문 382–383쪽과 법령 기준 PDF 777–778쪽/본문 711–712쪽의 종전 부칙 검토. 길라잡이 PDF 454–455쪽은 별표·서식 개정 사례이므로 규정 전체의 전부개정 형식 근거와 혼동하지 않는다.

**완료 기준:** 전부개정 작업에서 일부개정 제목·지시문이 나오지 않는다. 단순 용어 교체만 많은 사례를 분량만으로 전부개정 권고하지 않는다. 기존 부칙은 삭제 또는 승계 여부를 담당자가 확인하기 전까지 검토 대상으로 남는다.

### P1-2. 공식 의견제시 요청서의 ‘작성 완료본’ 제공

현재 `opinion_request` 모드는 서식의 요건을 설명하고 일반 초안을 만들며, 사용자가 제공한 원본 HWPX도 내려받을 수 있다. 작성한 내용이 공식 요청서의 칸으로 들어가는 전용 생성 과정은 확인되지 않았다.

원본 HWPX에서 확인한 입력 구조는 다음과 같다.

| 부분 | 원본 항목 | 앱에서 준비할 정보 |
| --- | --- | --- |
| 사전 확인 | 요청 주체, 자치법규 종류·소속/관련 기관 | 요청 기관·명의, 규정 종류, 관련 기관인 경우 관계 설명 |
| 사전 확인 | 입안·예고·심사·의회·의결·공포 단계 | 현재 단계와 확인된 의결·공포일 |
| 사전 확인 | 구체적 질의인지, 일반 해석인지 | 전체 적법성 질의를 쟁점별 질문으로 나누기, 사실판단과 해석 구분 |
| 사전 확인 | 국정과제, 지방시대 시행계획 관계 | 해당 여부와 확인된 번호·내용, 모르면 미확인 |
| 본문 1–2 | 질의배경, 질의요지 | 실제 배경과 한 질문에 한 쟁점 |
| 본문 3 | 대상 자치법규 조문·관련 법령 | 출처·기준일이 있는 조문 원문과 첨부 |
| 본문 4–5 | 갑설·을설, 요청기관·관계기관 의견 | 실제 존재하는 견해와 논거, 확인되지 않은 견해는 생성 사실로 취급하지 않기 |
| 본문 6 | 참고자료 | 판례·해석·의견·붙임 목록과 파일 |

AI는 문장을 정리하고 부족한 근거를 알려 주며, 체크표시·날짜·관계기관 의견은 담당자가 확정한다. 완성본은 원본과 구분한 HWPX로 저장하고, 원본 다운로드도 유지한다. 기존 프롬프트에는 예시 체크·갑설을 사실처럼 쓰지 말라는 보호가 이미 있으므로 이 원칙을 입력 구조와 출력 검사로 확장한다.

**자료 근거:** `public/references/opinion-request.hwpx`의 사전 점검표와 본문 1–6항. 고정 PDF 쪽수는 없는 자료다.

**완료 기준:** 미확인 항목은 `[작성 필요]`로 남고, 서식의 요청자·의결일 예시가 실제 입력값처럼 들어가지 않는다. 작성 항목의 누락 검사와 기관 한글 환경의 열기·수정·재저장 확인을 통과한다. 일반 문서 HWPX 출력 검증을 요청서 양식 충족 검증으로 대신하지 않는다.

### P1-3. 기관 규정 묶음과 별표·서식 영향 관리

현재 엔진은 규정 내부 조·항과 별표·서식의 인용을 다루며 변경한 별표·서식을 개정안에 붙인다. 상위법 영향 분석은 `ImpactInputs.institutionRaw` 한 본문을 받는다. 기관 전체 규정의 연결 관계를 저장하는 구조와는 다르다.

다음 단계는 문서 ID·종류·시행일을 가진 여러 기관 규정을 입력받아, 바뀐 조문을 참조하는 다른 규정·별표·서식을 후보로 보여 주는 것이다. 자동 치환 가능, 문맥 검토 필요, 대상 소실을 구분한다. 별표·서식은 현재 `Annex.text` 문자열이므로 표의 행·열, 병합 셀, 입력 칸을 보존하는 편집은 추가 설계가 필요하다.

**자료 근거:** 길라잡이 PDF 343–344쪽/본문 335–336쪽, PDF 454–455쪽/본문 446–447쪽의 별표·서식 개정, PDF 532–535쪽/본문 524–527쪽의 종합 점검 흐름. 단순 참조 관계 외에 실제 업무 의미가 달라지는지는 담당자 검토를 거친다.

**완료 기준:** 여러 규정에 동일한 ‘제5조’가 있어도 문서 식별자를 바탕으로 정확히 구분한다. 삭제된 조문을 인용하는 문장은 번호만 바꾸어 해결된 것으로 표시하지 않는다. 표·서식 구조를 보존하지 못한 입력에는 변환 범위와 원본을 함께 보여 준다.

## 5. 작지만 먼저 손볼 수 있는 내용

### 재검토기한 기본 위치

행정규칙 기준 [PDF 42쪽/본문 38쪽](../../public/references/administrative-rules-2025.pdf#page=42)은 존속기한과 재검토기한을 원칙적으로 **본칙 마지막**에 두도록 설명한다. 현재 `buildAddenda()`는 `reviewDeadline`이 선택되면 부칙에 재검토기한 작성란을 넣는다. 매뉴얼의 기본 배치와 다르므로 본칙 마지막 조문 작성으로 연결하거나 별도 확인 사항으로 제공하는 것이 적합하다.

이 차이를 모든 사례의 위법 판정으로 표현해서는 안 된다. 같은 기준 PDF 40–41쪽/본문 36–37쪽은 적용 대상과 제외 범위도 설명한다. 중앙행정기관의 일몰 기준을 모든 지방 규칙·내부 지침에 일괄 적용하지 않는다. 존속기한과 재검토기한의 효과도 동일하다고 설명하지 않는다.

### 관행적 ‘규칙으로 정한다’ 문장

길라잡이 [PDF 26쪽/본문 18쪽](../../public/references/local-ordinance-2026.pdf#page=26)은 단순 집행에 필요한 규칙을 위해 포괄적인 시행규칙 조항을 반드시 둘 필요는 없다고 설명한다. 이 문장이 주민의 새로운 의무를 정할 권한을 자동으로 주는 것도 아니다. 초안 생성기는 관행적으로 이 문장을 항상 넣기보다, 무엇을 규칙으로 정해야 하는지와 위임 범위를 확인해야 한다. 해당 문장 자체가 언제나 위법이라는 뜻은 아니다.

### 문장 정비에서 의미가 달라지는 지점 강조

쉬운 법령 기준 PDF 121–122쪽/본문 113–114쪽은 가운뎃점과 접속어의 해석 범위가 달라질 수 있음을 보여 준다. PDF 157쪽/본문 149쪽의 ‘과반수 이상’ 정비 예시는 ‘반수 이상’을 ‘과반수’로 바꾸라는 뜻이 아니다.

현재 의미 변경 검증을 유지하면서, 제안 카드에서 바뀌는 수치·기간·의무 표현·대상·접속어를 강조하고 ‘누가 추가되거나 빠지는가’를 확인하게 한다. 전체 카드를 주의색으로 만드는 것보다 위험한 변화 자체가 보이는 편이 판단에 도움이 된다.

## 6. 이어서 설계할 절차와 버전 관리

**예고 후 의견 처리:** 예고문 초안을 만든 다음에는 의견별 요지, 반영 여부, 처리 이유, 바뀐 조문을 연결하는 기록이 필요하다. 길라잡이 PDF 539–540쪽/본문 531–532쪽은 재예고 검토 사례를, PDF 541쪽/본문 533쪽은 예고 기재사항과 제출 의견 처리 관련 내용을 설명한다. 현재 문서 생성은 강점이지만, 확인한 코드에는 이 사건별 기록 구조가 없다. 단순히 ‘예고 완료’를 누르는 것보다, 예고 후 권리·의무·시행일이 크게 바뀌었을 때 담당자에게 재검토할 근거를 보여 주는 방식이 좋다.

**공포 후 아직 시행되지 않은 개정:** 법령 기준 PDF 843–844쪽/본문 777–778쪽에는 공포되었지만 시행 전인 규정의 추가 개정 방식이 나온다. 현재 앱은 시행예정 법령을 현행 근거로 쓰지 않도록 차단하고 유사 규정 비교 범위를 안내한다. 이 보호는 인정해야 한다. 후속 기능은 별도로 현행본·공포본·시행예정본을 구분하여 작업 기준본을 확정하고, 미시행 개정 작업에 필요한 번호·시점을 저장하는 것이다.

**기관별 발령·등재:** 행정규칙 기준 PDF 18쪽/본문 14쪽 및 PDF 22쪽/본문 18쪽의 중앙행정기관 절차를 지방자치단체나 공공기관 내부 지침에 그대로 적용하지 않는다. 기관 유형과 자체 규정에 맞는 절차 템플릿을 설정하고, 담당자가 추가한 기관 기준의 출처·개정일을 함께 저장한다.

## 7. 조목이의 역할과 인지 부담

매뉴얼의 흐름도를 그대로 긴 체크리스트로 옮기면 실무자의 판단 부담이 남는다. 조목이는 현재 단계에서 중요한 질문 한 가지와 이유를 짧게 안내하고, 근거 쪽은 펼쳐 볼 수 있게 연결하는 역할이 적합하다.

| 상황 | 조목이의 안내 예시 | 연결되는 실무 |
| --- | --- | --- |
| 새 의무를 넣는 조문 | ‘신고 의무가 생겼네요. 이 의무를 정할 수 있는 근거부터 같이 볼까요?’ | 조문별 위임 근거 확인 |
| 시행일을 정할 때 | ‘이미 접수한 신청은 어떻게 처리할까요? 이 부분이 부칙에 필요할 수 있어요.’ | 기존 업무 처리표 |
| 규정 전체를 크게 고칠 때 | ‘예전 부칙에 계속 필요한 내용이 있는지 챙겨 볼까요?’ | 종전 부칙 검토 |
| 문장 정비가 수치를 바꿀 때 | ‘읽기는 쉬워졌지만 적용 범위가 달라질 수 있어요. 바뀐 숫자를 확인해 주세요.’ | 의미 변경 비교 |
| 근거가 부족할 때 | ‘여기는 아직 판단할 자료가 부족해요. 필요한 조문을 확인해 주세요.’ | 확인할 근거와 원문 입력 |

캐릭터 표정과 축하는 저장·내려받기·검토 완료처럼 실제 상태가 확인된 순간에 사용한다. 귀여운 표정으로 미확인 판단을 확정된 것처럼 보이게 하지 않는다. 중요한 경고는 캐릭터 동작에 의존하지 않고 제목·구체적 이유·할 일을 함께 제시한다. 움직임 줄이기 설정과 정적 상태에서도 같은 정보가 전달되어야 한다.
