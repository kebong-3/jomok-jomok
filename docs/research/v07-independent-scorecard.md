# 조목조목 독립 평가표 — v0.6 실증과 v0.7 조목이 개선

평가일: 2026-10-26, 한국 시간. 기준 코드: v0.6.0 운영 반영 `2e191dc2c2671656464ea4b2fca36336a68ef1e0`. v0.7 구현 커밋은 `4db6db420e99aa786d915a3b38395c2c5b0d10b6`이며, 2026-10-27 한국 시간의 운영 검수 결과를 후속 반영했다.

## 1. 결론과 평가 범위

**현재 증거로 평가한 v0.6은 82/100점이다.** 활용성 32/40, 완성도 25/30, 확산 용이성 25/30이다. 이는 실제 심사 결과를 예측하는 공식 점수가 아니라, 공식 참가 안내서의 세션 2 배점과 이 저장소의 확인 가능한 구현·검증 기록을 바탕으로 한 독립 개발 검토자의 판단이다. 관점과 시연 조건에 따른 판단 범위는 약 78~86점으로 본다. 이 범위는 통계적 신뢰구간이 아니다.

**운영 데스크톱 UI 검수 후 v0.7의 자체 평가를 83/100점(활용성 32/40, 완성도 26/30, 확산 용이성 25/30)으로 반영했다.** 처음 제안했던 사용성 1점은 큰 캐릭터·표정 선택·정지/재개·키보드 조작·작업 상태 표시의 운영 확인에 근거한다. 모바일 실기기, OS 동작 줄이기 설정 전환과 스크린리더 사용자는 아직 실측하지 않았다. 반응형·동작 줄이기 지원은 코드 검수 범위다. [운영 검증](../VALIDATION-v0.7.md) 캐릭터 개선을 법령 검토 정확도, 업무시간 감소 또는 기관 이식 성공의 증거로 계산하지 않는다. 이번 자료 재검토에서 찾은 법제 기능 공백과 후속 기획은 구현 점수에 넣지 않는다.

핵심 제정·일부개정 작업, 개정안·대비표 생성, 근거 추적, 실패 후 재개, 선택 수정과 복구는 평가할 만한 구현이다. 높은 점수로 올라가는 데 남은 과제는 독립적인 결과 품질 검증, 실제 담당자의 업무효과, 다른 기관 환경에서의 운영 이관 증명이다. 현재 자료만으로 95점 또는 98점을 부여할 근거는 충분하지 않다.

## 4. 5개 원본 자료를 활용하는 수준에 대한 판단

핵심 원본은 PDF 4권과 의견제시 요청서 HWPX 1개, 합계 5종이다. 앱의 여섯 번째 파일은 사용자 출처 안내 TXT이다. 이를 법제 매뉴얼 6종 또는 학습 완료된 6개 전문자료로 확대해서 계산하지 않는다. 원본의 보관·검색·페이지 연결과 실제 업무 판단 지원은 단계가 다르다. [자료 목록](../../src/data/knowledge/manifest.json), [매뉴얼 재검토](v07-manual-audit.md)

현재는 원본 5종을 보관하고 검색한 발췌문을 AI에 제공하며, 인용이 실제 발췌문에 있는지 대조하는 단계가 구현돼 있다. 이는 좋은 기반이다. 반면 다음과 같은 어려운 업무가 별도 입력·출력 흐름으로 충분히 연결되지는 않았다.

| 공백 | 현재 구현과의 차이 | 점수상 의미 |
|---|---|---|
| 권한·위임 연결표 | 위임 근거 입력·조회와 일부 키워드 점검은 있다. 새 권리 제한·의무·인허가·신고 등을 어떤 수권 조항과 연결했는지 구조화한 표는 없다. | 활용성의 실무 판단 지원 |
| 적용례·경과조치 판단표 | 시행일과 경과조치 입력은 있다. 기존 신청·계약·위원 임기·처분에 어느 규정이 언제 적용되는지 경우별 대조표는 없다. | 활용성·복잡 사례의 산출물 품질 |
| 전부개정·폐지·의견제시 요청 완성 흐름 | 현재 작업 모드는 제정과 일부개정 중심이다. 의견제시는 RAG 준비와 원본 다운로드 수준이며 공식 요청서 항목을 채워 출력하는 흐름은 없다. | 지원 범위의 명확성, 다음 실무 확장 |
| 여러 규정을 묶은 영향 검토 | 단일 규정 인용 정비와 상위법 전후 영향 후보는 있다. 기관 규정 전체를 묶은 완전한 영향망은 아니다. | 기관 단위 확장의 후속 범위 |

이 공백은 이번 v0.7에서 구현했다고 계산하지 않는다. 사용자가 요구한 기본 제정·개정 기능이 전혀 없다는 의미도 아니다. 넓은 제품 설명에 비해 실제 지원 범위를 명확하게 제시하고, 필요한 기능부터 확장해야 한다는 판단이다.

검색 개발 질의에서 자료 지정 60/60, 전체 검색 58/60이라는 기록은 개발 과정에서 보정한 질의의 검색 적중도다. 독립 법제 정답률이나 해당 원문이 결론을 뒷받침하는 비율로 계산하지 않는다. 실제 서버 검증기는 인용문 존재와 변경 전 문장의 일치, 일부 수치·의무·조건 표현을 검사한다. [검색 평가의 범위](v04-rag-review.md), [응답 검증기](../../src/server/knowledge-answer.ts)

## 5. 높은 점수에 도달하기 위한 세 가지 우선순위

아래는 후속 개발·검증 계획이다. 실행 전에는 가점을 미리 부여하지 않는다. 같은 결과를 활용성과 완성도 양쪽에 반복해서 더하는 방식도 사용하지 않는다. 95점대라는 목표는 모든 항목의 증거가 충분해졌을 때 다시 평가할 대상이며 보장값이 아니다.

### 우선순위 1 — 어려운 판단 세 가지를 실제 산출물로 연결

권한·위임 연결표, 적용시점 판단표, 의견제시 요청서 완성 흐름을 우선한다. 이 세 가지는 매뉴얼 문장을 보여 주는 데서 담당자가 다음 행동을 정하고 문서를 완성하는 단계로 연결하기 좋다.

- 입력한 사실·법령 원문·매뉴얼 원칙·미확정 사항을 구분한다.
- 조문별 권리·의무나 기존 관계의 변화를 표로 제시하고, 관련 원문 페이지로 이동할 수 있게 한다.
- 담당자가 이미 입력한 기관·조문·배경을 재사용해 요청서와 검토 메모를 작성한다.
- 기능 추가 후 대표 사례와 반례를 별도로 준비해 적용 범위를 검증한다.

가점 검토 대상은 활용성의 절차·누락 방지와 산출물 연결이다. 단순히 탭 세 개를 추가했다고 가점을 주지 않는다.

### 우선순위 2 — 독립 사례와 실제 담당자로 품질·효과 확인

다음은 권장 시험 설계이며 공식 공모 요건이 아니다.

- 법제 담당자와 일반 사업부서 담당자가 함께, 제정·일부개정·부칙·권한·인용 정비 등 미리 공개하지 않은 사례 20개 이상을 평가한다.
- 근거 적절성, 중대한 법적 오류, 누락된 검토사항, 개정안·대비표의 일치, 최종 문서의 수정량을 평가한다. 단순 인용 존재율과 분리한다.
- 실제 직원 5~8명 정도가 기존 방식과 앱 사용 방식으로 비슷한 난도의 업무를 수행하고 순서를 바꾸어 익숙해진 효과를 줄인다.
- 초안 도달시간, 검토 후 완료시간, 도움 요청 수, 수동 수정 수, 남은 오류를 함께 기록한다. 속도만 좋아지고 오류가 늘어난 경우 성공으로 계산하지 않는다.
- 실제 사용하는 한컴 한글에서 HWPX를 열어 편집·저장·인쇄하고, 글꼴·표·페이지 나눔·밑줄을 확인한다.

가점 검토 대상은 실증된 기대효과, 결과 품질과 사용성이다. 시험 규모가 작으면 그 한계도 함께 제시한다.

### 우선순위 3 — 두 번째 기관에서 설치·복구·모델 교체 시연과 제출 세트 완성

- 현재 개발 환경을 재사용하지 않고, 두 번째 기관의 새 환경에 문서대로 설치한다.
- 기관 프로필과 작업 보관파일을 가져오고 문서 출력을 재현한다.
- 다른 제공자 또는 기관의 승인된 호환 모델로 바꾸어 같은 대표 사례를 실행한다.
- 공개·내부망 운영별로 데이터 경로, 필요한 권한, 키 관리, 사용량 확인, 장애 대응과 자료 갱신 책임을 정리한다.
- 판본을 갱신했을 때 예전 작업의 인용 근거를 어떻게 확인할지 기록한다.
- 검증한 동일 버전을 기준으로 공공 GitLab 등록, 양식 2-1 구동안내서 PDF와 최신 시연 MP4를 묶는다. 시연 진행안과 실제 녹화, 연결 시험과 주요 기능의 모델별 실행 증거를 구분한다.

가점 검토 대상은 이식성과 정식 개발·운영 이관이다. Dockerfile이 존재한다는 사실과 새 환경에서 설치가 성공했다는 사실은 별도로 증명한다. 제출물 완성은 실제 심사를 받을 수 있도록 준비하는 일이며, 제출했다는 사실만으로 높은 제품 점수를 부여하지 않는다.

## 6. v0.7 조목이의 가점 조건과 감점 위험

조목이의 목적은 담당자가 시작 버튼과 다음 행동을 쉽게 찾고, 기다리는 동안 작업이 진행 중임을 이해하도록 돕는 것이다. 다음 항목을 검수 기준으로 삼았다. 운영 데스크톱에서 시작 행동·표정·키보드·정지/재개와 상태 안내를 확인해 사용성 1점을 반영했다. 작은 화면·시스템 동작 설정은 코드 검수로 한정하며 추가 실기기 검증이 필요하다.

1. 첫 화면에서 조목이와 작업 시작 행동을 함께 볼 수 있다.
2. 인사·웃음·생각 등 표정이 실제로 구분되고, 조문 작성·검토·완료 상태와 어울린다.
3. 표정 선택을 키보드로 사용할 수 있고 현재 선택을 알 수 있다.
4. 반복 동작을 쉽게 멈출 수 있으며 시스템의 동작 줄이기 설정을 존중한다.
5. 모바일에서도 캐릭터가 입력·시작 버튼을 밀어내거나 덮지 않는다.
6. 캐릭터의 웃음·축하를 법률적 적합성 승인이나 최종 결재 완료로 표현하지 않는다.

캐릭터를 크게 만들면서 주요 행동을 첫 화면 밖으로 밀어내거나, 계속 움직여 긴 글을 읽기 어렵게 하거나, 표정 전환마다 보조기기가 불필요하게 읽게 하면 사용성 가점을 보류한다. 캐릭터 화면 검증만으로 초보 담당자의 전체 과제 성공률이 확인되는 것은 아니다.

## 7. 출품 설명에 사용할 수 있는 표현

확인 가능한 표현은 “제정·일부개정의 초안과 문서 세트를 만들고, 원문 근거를 추적하며, 선택한 수정과 되돌리기를 지원한다”, “424개 자동 검사와 제한된 운영 사례를 검증했다”, “기관 설정·작업 보관·모델 연결을 이전할 수 있도록 구현했다”이다.

현재 근거가 없는 표현은 “법령 정확도 98%”, “업무시간 80% 절감”, “모든 한글 환경에서 오류 없음”, “모든 기관이 즉시 도입 가능”, “실제 심사에서 98점 이상 보장”이다. 제출 자료는 구현 수준, 시험 조건, 실제 효과와 향후 계획을 나누어 제시하는 편이 검증 가능한 강점을 잘 보여 준다.
