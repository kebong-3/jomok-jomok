# v0.4 다섯 역할의 검토와 채택 결정

기준: 2026-10-25 인수인계판. 자료 분석·구현·교차검토에서 나온 판단을 운영 인수인계용으로 묶었다. 다섯 역할은 개발 과정의 역할 분담이다. 앱의 모든 요청마다 다섯 LLM이 회의하거나 다수결로 적법성을 판정하는 구조를 구현했다고 뜻하지 않는다.

[검색 전문 검토](v04-rag-review.md), [핵심 업무·품질 검토](v04-quality-review.md), 현재 코드와 원본을 함께 기준으로 삼는다. 작업 공간 복구 과정에서 과거 개별 검토 파일이 모두 보존된 것은 아니므로, 이 문서는 없는 회의록이나 누락된 검토 파일의 원문을 재현했다고 표시하지 않는다. 현재 구현의 확인 범위는 [v0.4 검증 기록](../VALIDATION-v0.4.md)을 따른다.

## 1. 역할과 검토 질문

| 역할 | 담당 관점 | 우선 검토한 질문 |
|---|---|---|
| 자치법규 실무 | 조례·규칙의 권한·위임, 절차와 부칙 | 해당 기관의 사무와 위임 범위를 확인할 수 있는가? 개정 방식의 예외를 빠뜨리지 않는가? |
| 법령·행정규칙 입안 | 조문 체계, 훈령·예규·고시, 개정문과 전환 관계 | 법령·조례·행정규칙의 적용 범위를 섞지 않는가? 시행 전 개정과 종전 부칙을 확인하도록 하는가? |
| 알기 쉬운 법령 | 용어·문장과 법적 의미 | 쉬운 문장 제안이 숫자·권리·의무·조건을 바꾸는가? 예시를 자동 치환 사전으로 오인하지 않는가? |
| 원문 검색·RAG | 페이지 추출, 검색, 출처와 생성 입력 | 답변의 근거가 실제 원문인가? 관련 예외를 회수하며 원본을 열 수 있는가? |
| 업무·품질·확산 | 실제 흐름, 실패 처리, 기관 이전, 평가 증거 | 제정·개정을 문서까지 끝낼 수 있는가? 모델·기관을 바꾸고 작업을 복원할 수 있는가? |

핵심 의사결정은 자료를 많이 넣는 것보다 **실제 업무의 근거·변경·문서·검토 기록이 연결되는지**를 우선했다. 사용자 필수 기능인 제정 체계·초안과 개정안·신구조문대비표는 같은 작업 흐름 안에서 유지한다.

## 2. 토론에서 채택한 결정

### ① 매뉴얼 근거와 현행 위임 근거를 구분한다

자치법규·입안 역할은 매뉴얼의 좋은 설명을 실제 기관의 권한 근거처럼 쓰는 위험을 제기했다. 검색 역할은 출처 메타데이터를 보존하고, 품질 역할은 화면과 백업에서 구분이 사라지지 않아야 한다고 보았다. 이에 `KB-…` 입안 참고자료와 `EV-…` 작업·법령 원문을 별도 계약으로 보관하고, 프롬프트에서도 매뉴얼을 현행 법령·수권 근거로 표현하지 않도록 했다. [근거 계약](../../src/lib/knowledge.ts) · [프롬프트](../../src/server/prompts.ts)

### ② 고정 참고자료는 추가 서비스 없이 검색한다

초기 자료는 6종으로 범위가 정해져 있다. 검색 역할은 서버 로컬 검색을 제안했고, 확산 관점에서는 임베딩 API와 벡터 DB의 별도 비용·계정을 필수로 만들지 않는 쪽을 채택했다. 실제 발췌를 AI 입력에 전달하는 RAG는 구현하되 모델 추가 학습·벡터 검색을 했다고 표현하지 않는다. 비공개 문서의 지속 업로드·권한별 검색은 별도 확장 과제다. [RAG 구조](../RAG-ARCHITECTURE.md)

### ③ 짧은 기준문만 검색하고 예외를 놓치지 않도록 한다

자치법규 역할은 개정량 기준이나 재검토기한 체크리스트만 검색될 때 적용 범위를 오인할 수 있다고 지적했다. 검색 역할은 본문 우선, 규정 종류·검토 방식 가중치, 같은 문맥의 인접 예외 보강을 적용했다. 같은 페이지·인접 페이지라는 이유만으로 무관한 사례를 붙이지 않으며 특정 정답 쪽을 코드에 박아 넣지 않는다. 일부개정·전부개정처럼 두 입안 주제를 선택하는 질문의 기준과 예외를 함께 회수하는 회귀 질문도 유지한다.

### ④ 페이지와 출처를 실제 파일에 연결한다

검색·품질 역할은 PDF 물리 페이지와 인쇄 쪽수를 분리하고 원본 파일을 그대로 제공하도록 결정했다. 알법 부록처럼 쪽수가 다시 시작하는 경우를 구분하고 HWPX에 가상의 PDF 페이지를 붙이지 않는다. 원본 SHA-256, 발췌 지문, 정본 인용 색인은 각각 다른 범위를 확인한다. 원문 지문이 맞아도 자료의 최신성과 해석의 타당성까지 검증됐다는 뜻은 아니다.

### ⑤ 문장 정비가 내용 변경을 숨기지 않도록 한다

알법 역할은 정비 전후 사례에 수치·조건 변경이 섞여 있을 수 있고 의무·재량·연결어의 차이가 중요하다고 보았다. 생성 단계는 표현 정비와 내용 변경을 나누고, 서버는 숫자 순서·의무·허용·부정·범위 표현의 변화를 별도로 표시한다. 변경 전 문장은 사용자 입력에 실제로 있어야 한다. 이 규칙이 모든 의미 변화를 완전히 탐지한다는 주장은 하지 않는다. [검증기](../../src/server/knowledge-answer.ts)

### ⑥ 인용이 확인되지 않은 답변을 그대로 내보내지 않는다

품질 역할은 존재하는 출처 ID를 붙였다는 이유만으로 답변을 신뢰할 수 없다고 지적했다. 서버가 제공한 발췌 안에 실제 인용문이 있는지 대조하고, 무효 인용·변경은 제외한다. 일부 항목이 제거되면 그 항목에 기대어 작성됐을 수 있는 요약·초안을 그대로 유지하지 않는다. 답변 근거가 하나도 남지 않으면 설명을 보류한다. 이는 인용의 기계적 검사이며 법리 판단은 별도다.

### ⑦ 제·개정 작업의 본문과 검색 기록을 이어간다

자료실을 별도의 챗봇으로만 두지 않고 개정 계획, 제정 체계·초안, 이유·주요내용, 점검 정비와 영향 검토에 실제 검색 자료를 전달한다. 작업에서 자료실로 이동할 때는 질문과 현재 본문을 같은 탭의 임시 세션으로 넘긴다. 제정 초안의 원본 입력칸이 비어 있다는 이유로 검토 본문까지 빠지지 않도록 작성된 초안을 사용한다. 개정은 수락한 변경이 반영된 본문이라는 점을 안내한다. 질문·본문은 URL에 넣지 않는다.

### ⑧ 긴 답변 때문에 실제 작업이 멈추는 문제를 먼저 고친다

운영 검증에서 짧은 Gemma 연결 시험이 성공해도 자료실의 긴 실제 요청이 시간 초과할 수 있었다. 또한 자동 연결의 마지막 Groq 인증 오류가 먼저 발생한 생성 실패를 가리는 문제가 있었다. 이를 실제 성공으로 계산하지 않고, 생성 입력·출력 분량과 요청 예산, 안전한 오류 요약을 보완하는 방향을 채택했다. 자료실은 최대 6개·본문 합계 5,500자의 참고자료와 핵심 설명을 사용한다. 수정이 실제 문제를 해결했는지는 운영 재검증 기록으로 확인한다.

### ⑨ 예시·설정·실제 성공을 구분한다

키가 등록된 상태, 짧은 모델 시험 성공, 실제 제정·개정 완료는 다른 증거다. 예시 응답은 예시라고 표시하고 모델 비교나 연결 시험에서 다른 모델의 응답으로 성공을 꾸미지 않는다. 모든 연결이 실패하면 분류된 오류를 남기며 키나 제공자의 원문 오류를 사용자에게 노출하지 않는다. 작업 기록의 실제 모델·프롬프트 버전과 문서 결과를 함께 확인한다. [모델 어댑터](../../src/server/llm.ts)

### ⑩ 유사 규정은 실제 두 원문을 비교한다

타 기관 규정의 존재는 우리 기관의 권한 근거가 아니다. 공식 API로 확인한 원문을 최대 두 개 선택하고 실제 조 제목·본문을 비교하도록 했다. 조 번호가 같다는 이유로 내용이 대응된다고 추정하지 않는다. 제목·식별자·시행일·조회 방식과 부분 조회 상태를 확인하며 저장본을 현행 공식 비교 결과로 꾸미지 않는다. [유사 규정 검증](../../src/lib/similar-rules.ts)

### ⑪ 문서 세트는 같은 변경 명세에서 만든다

입안·품질 역할은 AI가 개정문과 대비표를 각각 자유롭게 작성하면 불일치가 생길 수 있다고 보았다. 수정 연산을 공통 명세로 만들고 담당자 수락 후 엔진이 개정문·대비표·인용 이동을 계산한다. 이유·주요내용은 현재 변경 내용과 맞춰 작성하며 내용이 바뀌면 검토 상태를 다시 확인한다. DOCX와 HWPX의 구조 검사, 실제 한글에서 열기·편집·인쇄는 별도 검증으로 구분한다. [문서 생성](../../src/lib/docs.ts)

### ⑫ 기관 설정은 작업에 함께 보관한다

확산 역할은 기관명만 바꾸는 수준보다 공고번호·연락처·서식·절차를 편집하고 옮길 수 있어야 한다고 보았다. 기관 프로필을 JSON으로 이전하고 새 작업에 스냅샷을 보관한다. 이후 기관 설정 수정·삭제로 기존 작업 문서가 바뀌지 않게 한다. 가져온 기관은 새 ID와 미확인 상태를 부여하며, 입력한 예고일수를 법적으로 확정된 기간으로 표현하지 않는다. [기관 설정](../../src/config/profiles.ts)

### ⑬ 기록과 복원을 함께 제공한다

작업 JSON에는 원문·변경·검토 상태·기관 스냅샷·참고자료 기록을 보관하며 API 키와 연결 설정은 제외한다. 참고자료는 정본 지문과 대조한다. 역할별 최근 검색 최대 12개를 보존하는 기능을 전체 영구 감사 로그라고 표현하지 않는다. 문서 ZIP에는 근거 원문과 검색 기록을 함께 제공해 담당자가 결과의 출처를 다시 확인할 수 있게 한다. [작업 이전](../../src/lib/project-transfer.ts)

### ⑭ 평가 점수는 실제 업무 증거로 보완한다

60개 개발 질문의 검색 결과는 검색기 개선에 사용된 자료다. 별도 검토 질문도 보정에 사용한 뒤에는 독립 시험 세트로 주장하지 않는다. 전체 테스트 수와 검색 적중률을 법률 정확도나 98점으로 환산하지 않는다. 실제 직원의 작성시간·수정 건수·누락, 독립 법제 검토와 다른 기관 설치 결과를 추가해야 활용성과 확산성을 입증할 수 있다.

| 지표 | 배점 | 구현과 연결되는 증거 | 추가로 필요한 실증 |
|---|---:|---|---|
| 활용성 | 40 | 제정·개정 문서 세트, 실제 근거와 원문 링크, 영향 후보, 유사 규정 비교, 기관 절차 설정 | 같은 난이도 업무의 수기 대비 시간·수정·누락, 여러 기관 담당자의 사용 결과 |
| 완성도 | 30 | 실제 AI 성공·실패 구분, 인용 대조, 엔진 정합성, 원본 다운로드, 백업·복원, 자동 검사 | 실제 한글의 열기·편집·인쇄, 장시간·모바일 사용, 기관 안건의 최종 검토 |

## 4. 완료 판단에 사용하는 실제 흐름

제정은 목적·근거 입력 → 조문 체계 확인 → 실제 초안 생성 → 조문 검토 → 이유·주요내용 → 문서 내려받기로 확인한다. 개정은 현행 원문·개정 의도 → 실제 변경 제안 → 담당자 수락 → 개정문·대비표 → 이유·부칙 확인 → 문서 내려받기로 확인한다. 이때 예시 응답 사용 여부, 실제 모델, RAG 검색 기록, 최종 파일 내용이 서로 맞아야 한다.

자료실은 정상 질문의 실제 인용 답변뿐 아니라 무관 질문의 근거 부족, 모델 실패 시 원문 유지, 잘못된 인용 제외도 확인한다. 기관 이전은 설정 JSON과 작업 JSON의 역할을 나눠 확인한다. 아직 실행하지 않은 항목을 문서만으로 완료 표시하지 않는다. 최신 결과와 남은 범위는 [검증 기록](../VALIDATION-v0.4.md)을 따른다.
