# 입안 자료 RAG 구조와 갱신 안내

기준: 2026-10-25 인수인계판. 구현 설명과 운영 성공 기록은 구분한다. 실제 시험한 커밋·모델·범위는 [검증 기록](VALIDATION-v0.4.md), 연결 설정은 [API 안내](API-SETUP.md)를 확인한다.

## 1. 제공하는 기능과 자료 범위

핵심 자료 5종과 출처 안내 1종을 앱에 보관하고, 질문과 관련된 실제 발췌문을 서버에서 검색해 AI 입력에 넣는다. 답변에는 해당 자료의 제목·판본·물리 페이지·원문 링크를 붙인다. 이는 검색 증강 생성(RAG)이며 모델의 가중치를 추가 학습한 방식은 아니다. 고정된 이 자료를 검색하기 위해 임베딩 API나 벡터 데이터베이스를 따로 연결할 필요는 없다.

| 자료 | 원본 형식 | PDF 물리 페이지 | 주요 활용 |
|---|---|---:|---|
| 자치법규 입안 길라잡이 2026 | PDF | 571 | 자치입법 권한, 조례·규칙, 개정 형식, 부칙 |
| 법령 입안·심사 기준 | PDF | 880 | 법령 체계, 입안 방식, 개정문, 적용례·경과조치 |
| 행정규칙 입안·심사 기준 2025 | PDF | 152 | 훈령·예규·고시, 발령 권한, 적용 범위 |
| 알기 쉬운 법령 정비기준 제10판 수정·증보판 | PDF | 394 | 용어·문장 정비와 의미 변경의 구분 |
| 자치법규 의견제시 요청서 | HWPX | 고정 쪽수 없음 | 요청 준비 항목과 서식 |
| 사용자 출처·파일 안내 | TXT | 없음 | 출처와 제공 기록 확인 |

현재 manifest 기준 원본 합계는 20,712,230바이트, PDF 합계는 1,997쪽, 검색 단위는 2,283개다. 파일별 SHA-256, 수록 시점, 수집·제공 시점과 원본 이름은 [manifest](../src/data/knowledge/manifest.json)에 있다. 사용자의 출처 안내문은 법적 수권 근거로 취급하지 않는다. 원본 파일은 `public/references`에 있으며 자료실에서 각각 내려받을 수 있다.

매뉴얼 판본의 연도는 개별 법령의 현행성을 증명하지 않는다. 인쇄 쪽수가 없는 표지나 HWPX에 가상의 쪽수를 부여하지 않으며, PDF 뷰어의 페이지와 책자의 인쇄 번호를 구분한다. 부록에서 인쇄 번호가 다시 시작하는 경우도 별도로 표시한다.

## 2. 구성 요소와 데이터 흐름

| 위치 | 책임 |

| `data/knowledge/corpus.json.gz` | 서버가 읽는 전체 발췌문 |

자료실 요청은 입력 검증 → 서버 검색 → 근거가 있으면 선택 모델 호출 → 인용 대조 → 화면 표시 순서로 처리한다. 모델이 제시한 출처 목록이나 클라이언트가 주입한 참고문서를 검색 결과로 믿지 않는다. 서버가 고른 실제 발췌문만 답변 검증의 출처 집합이 된다. 전체 코퍼스는 브라우저로 전송하지 않는다.

일반 제·개정 작업에서는 개정 계획, 제정 조문 체계, 제정 초안, 이유·주요내용, 삭제 조문 정비와 상위법 영향 검토 역할에 관련 자료를 추가한다. 개정문·신구조문대비표·인용 번호 정리는 공통 변경 명세를 사용하는 엔진이 계산한다. RAG 답변 자체가 담당자 수락 없이 기존 작업의 변경 명세를 바꾸지는 않는다.

## 3. 추출과 원문 대조

[빌드 스크립트](../scripts/build_knowledge.py)는 원본 SHA-256과 PDF 페이지 수를 먼저 확인한다. PDF는 `pdftotext -layout`으로 물리 페이지 단위 텍스트를 추출하고, HWPX는 압축 안의 section XML에서 문단 문자열을 읽는다. 문장을 정규화한 뒤 최대 1,250자, 겹침 160자를 기준으로 발췌한다. PDF의 서로 다른 물리 페이지를 하나의 발췌로 합치지 않는다.

발췌 ID에는 문서 ID·물리 페이지·발췌 순서가 들어간다. `contentHash`는 발췌 본문의 지문이며, 정본 인용 색인은 ID·문서·물리 페이지·책자 쪽·절·절 유형·본문을 함께 대조한다. 백업의 본문과 외부 체크섬을 함께 수정하더라도 앱에 등록된 정본과 달라지면 공식 참고 인용으로 복원하지 않는다. 이 대조는 공인 전자서명이나 법적 효력을 부여하는 기능은 아니다.

현재 추출은 이미지 OCR, 표 셀 병합 관계와 도표의 의미를 완전히 복원하지 않는다. 전체 페이지를 처리했다는 사실과 모든 시각 요소의 의미를 이해했다는 주장은 다르다. 중요한 문구는 답변의 PDF 링크에서 앞뒤 문맥을 확인한다.

## 4. 검색 방식

검색은 BM25 계열 단어 점수, 한국어 주제어, 2·3음절 문자 매칭을 결합한다. 띄어쓰기·조사 차이와 업무상 동의 표현을 보완하되, 문자 조각이 우연히 겹친 결과를 관련 근거로 반환하지 않도록 직접 주제와 질의 커버리지를 확인한다. 본문과 구체적인 소제목을 목차·일반 머리말보다 우선한다. [검색 구현](../src/server/knowledge.ts)

규정 종류와 검토 방식은 우선순위를 조정한다. 예를 들어 알기 쉬운 문장 검토에서는 알법 자료를, 의견제시 요청 준비에서는 공식 서식을 우선한다. 이 조건이 다른 일반 기준을 모두 숨기거나 해당 자료의 모든 내용을 자동 적용하라는 뜻은 아니다.

비교·선택 질문에서는 질문의 두 입안 주제가 함께 등장하는 선택·구별 절을 우선하고, 같은 문맥에서 다음 물리 페이지로 이어지는 번호 목록·예외를 함께 찾도록 보완한다. 검색 결과의 ID와 원문은 그대로 유지하며, 특정 정답 페이지 번호를 코드에 넣어 보내는 방식은 사용하지 않는다. 인접 페이지라는 이유만으로 무관한 판례·구법 사례를 붙이지 않는다.

제·개정 역할별 자동 검색은 담당자의 개정 의도·목적을 먼저 찾고, 역할에 필요한 일반 기준을 제한적으로 보강한다. 같은 문맥의 예외와 종전 규정 설명을 함께 전달할 수 있지만 모든 예외를 빠짐없이 회수한다는 보장은 없다. 세부 검색 판단과 개발 반례는 [검색 검토 기록](research/v04-rag-review.md)에 있다.

## 5. 두 AI 흐름의 입력 한도

| 흐름 | 참고자료 한도 | 별도 입력 |
|---|---|---|
| 자료실 `knowledge_assist` | 최대 6개, 발췌 본문 합계 5,500자 | 질문 2,000자, 본문 12,000자, 요청 본문 65,000바이트 |
| 제·개정 역할별 `retrieveForRole` | 관련 자료와 예외·일반 기준을 합쳐 최대 6개, 메타데이터를 포함한 계산 예산 약 7,000자 | 각 역할이 필요로 하는 실제 원문과 EV 근거 |

자료실의 `review`, `plain_language`에는 검토할 본문이 필요하다. v0.8 자료실 경로는 질문과 입력 본문 전체(최대 12,000자)에서 권한·부칙·형식·문장·의견제시·절차 쟁점을 찾고 각각 검색한다. 쟁점별 후보를 순환 선택하면서 최대 6개·5,500자 예산을 유지한다. `coverage`에 입력 조문, 쟁점별 근거 미발견과 예산 제외를 보존한다. 자동 탐지한 쟁점은 검토 완료 판정이 아니다. 일반 제·개정 역할별 `retrieveForRole` 경로와도 구분한다. 위 수치는 전체 제공자 토큰 수를 뜻하지 않으며 프롬프트와 JSON 구조는 별도로 더해진다.

자료실 프롬프트는 핵심 설명 2~4개, 짧은 실제 인용, 중요한 변경 제안 3개 이내로 답변을 구성한다. 초안은 사용자가 요청한 경우에만 작성하도록 제한한다. 이 제한은 공개 서버의 요청 시간 안에서 검토가 끝나도록 하는 선택이며, 더 많은 쟁점은 질문을 나눠 검토한다. 원문 인용 검증을 생략하거나 잘린 응답을 완성된 결과로 처리해 속도를 높이지 않는다.

## 6. 답변 검증과 실패 상태

[답변 검증기](../src/server/knowledge-answer.ts)는 다음을 검사한다.

1. 서버가 전달한 출처 ID인지 확인한다.
2. NFC·공백 정규화 후 인용문이 해당 발췌에 실제로 존재하는지 대조한다.
3. 변경 제안의 `before`가 사용자 입력 본문에 그대로 존재하는지 확인한다.
4. 숫자 순서, 의무·허용, 부정 표현, 범위·연결어 등의 변화는 내용 변경 검토 대상으로 표시한다.
5. 근거가 없는 항목을 제외한다. 일부 항목을 제외하면 기존 요약을 중립 안내로 바꾸고 그 항목에 의존할 수 있는 초안도 그대로 재사용하지 않는다.

| 결과 | 처리 |
|---|---|
| 검색 근거 없음 | AI를 호출하지 않고 `insufficient` 반환 |
| 검색 성공·AI 실패 | 실제 원문은 남기고 `ai_unavailable` 표시 |
| AI의 인용을 확인할 수 없음 | 설명을 보류하고 원문 확인 안내 |
| 일부 인용·변경만 유효 | 유효 항목과 제외 경고를 함께 표시 |
| 답변 구조·인용 검사 통과 | `answered`와 실제 모델 trace 표시 |

문구의 존재 검증은 법적 해석의 타당성 검증과 다르다. 유효한 인용을 붙인 결론도 해당 기관에 적용되지 않을 수 있다. `KB-…`는 매뉴얼 참고자료, `EV-…`는 법령·위임문·작업 원문으로 구분하며, 매뉴얼을 찾았다는 이유로 현행 상위법이나 위임 확인을 완료 처리하지 않는다.

## 7. 작업 문맥과 보관파일

작업 화면에서 자료실로 이어갈 때 질문과 본문은 같은 탭의 `sessionStorage`에 보관하고 15분 안에 한 번 읽는다. 질문·본문을 URL에 넣지 않는다. 제정은 작성한 초안, 개정은 현재 수락한 변경을 반영한 본문을 전달한다. 본문이 12,000자를 넘으면 일부만 자동 전달하지 않고 범위를 직접 선택하도록 안내한다.

`KnowledgeRecord`에는 역할, 검색어, 검색 시각, 자료 버전, 상태와 실제 전달 발췌문을 남긴다. 같은 역할은 최근 기록으로 바꾸며 최대 12개 역할 기록을 유지한다. 전체 실행을 영구 보관하는 감사 로그는 아니다. 문서 ZIP의 `입안참고자료_검색기록.txt`와 작업 JSON으로 이 기록을 옮길 수 있다. API 키·연결 설정은 보관파일에 포함하지 않는다. [프로젝트 보관](../src/lib/project-transfer.ts)

## 8. 운영 배포와 자료 갱신

기존 자료로 앱을 실행할 때 필요한 런타임은 Node.js이며 Python·Poppler는 재추출 단계에만 필요하다. Next.js는 `/api/llm`, `/api/diag`, `/api/knowledge/*`에 코퍼스 파일을 추적 포함한다. Docker는 standalone 결과와 `public`, `data/knowledge`를 함께 복사한다. [Next 설정](../next.config.ts) · [Dockerfile](../Dockerfile)

원본이나 기준서를 교체할 때는 다음 순서로 진행한다.

1. 공식 판본과 원본 파일, 출처·이용 조건, 수집 시점을 확인한다.
2. `scripts/build_knowledge.py`의 문서 정의, 원본 SHA-256, 페이지 수, 원본 이름 접두사와 자료 버전을 갱신한다. 임의 파일을 폴더에 넣는 것만으로 자동 등록되는 기능은 아니다.
3. 원본을 분리된 입력 폴더에 두고 Python의 `pypdf` 및 Poppler의 `pdftotext`가 있는 환경에서 재생성한다.
4. manifest·코퍼스·인용 색인·coverage·원본 파일을 함께 확인한다. 물리 페이지와 인쇄 쪽 대응을 실제 원본에서 재확인한다.
5. 기존 질문과 새 판본의 변경·예외 질문을 시험하고 실패 결과를 남긴다. 기존 질문의 예상 쪽은 판본 변경이 확인된 경우에만 근거를 남겨 갱신한다.
6. 운영 빌드에 색인이 포함됐는지 확인하고 배포 후 실제 검색, 원본 다운로드, AI 답변을 각각 확인한다.

```bash
python scripts/build_knowledge.py --input /path/to/attachments
npx vitest run tests/knowledge-search.test.ts tests/knowledge-answer.test.ts tests/knowledge-assist.test.ts tests/knowledge-integrity.test.ts
KNOWLEDGE_BENCHMARK=1 npx vitest run tests/knowledge-search.test.ts
npm run build
```

색인 버전과 정본 지문이 바뀌면 이전 백업에 든 인용의 복원 가능성을 별도로 확인해야 한다. 장기 운영에서는 버전별 정본을 유지하거나 이전 기록의 검증 상태를 명시하는 마이그레이션 설계가 필요하다.

## 9. 평가와 확장

60개 개발 질의의 검색 적중 기록은 [실측 JSON](validation/v04-retrieval-benchmark.json)에 있다. 자료 지정 검색과 전체 자료·종류·모드 검색을 구분한다. 이 질문들은 토큰화·순위 개선에 사용됐으므로 독립 시험 정확도나 법리 답변 정확도로 제시하지 않는다. 8개 추가 반례 역시 보정에 사용한 이후에는 개발 반례다. 실제 최신 통과 수·속도·실패 항목은 검증 기록과 실행 파일을 기준으로 한다.

기관에서 비공개 문서를 계속 추가하려면 자료별 접근권한, 삭제·갱신 절차, 임베딩·재순위화의 효과, 저장소와 감사 기록을 별도 설계해야 한다. 현재 구현은 고정된 공개 참고자료 6종을 이식하기 쉬운 방식으로 사용하는 범위다. 업무효과는 실제 직원의 작성시간·수정 건수·누락과 최종 제출 품질을 같은 기준으로 비교해 확인해야 한다. 검색 점수만으로 대회 98점이나 법률 정확도를 보증하지 않는다.
