로컬 런타임은 Node 24.19.0이다. 프로젝트의 운영 기준은 Node 22이며 GitHub CI에서도 Node 22를 사용한다. 최종 커밋의 CI 결과는 배포 확인 절에 기록한다.

Windows의 기본 텍스트 줄바꿈 변환이 출처 안내문 원본의 바이트를 바꾸는 문제를 확인했다. 원본 바이트를 복원하고 public/references에 -text 속성을 지정했다. 원본을 새 내용으로 고치거나 manifest의 예상 지문을 변경해 검사를 통과시키지 않았다.

## 업무별 확인

1. 조문별 근거는 자치사무·위임 사무·기관 내부 사무, 주민의 새 제한·의무, 정확한 인용과 적용 범위를 기록한다. 참고 조례·매뉴얼·일반 메모는 수권 근거로 인정하지 않는다. 확인이 완료돼도 적법성 승인으로 표시하지 않는다.
2. 기존 신청·계약·위원 임기·제재·서식 준비는 기준 사건과 적용 규정, 적용례·특례·경과조치를 구분한다. 답변이 없거나 현재 본문 지문이 다르면 해당 문장을 부칙에서 제외하고 기록에 남긴다.
3. 재검토기한은 부칙 자동 삽입을 제거했다. 기관 유형과 적용·제외 근거를 확인한 뒤 명시적으로 본칙 마지막 조문에 추가한다. 이미 같은 조문이 있거나 현재 초안이 바뀌면 중복·오반영을 막는다.
4. 전부개정은 새 본칙 전체와 별표·서식을 직접 편집하며 전용 개정문을 출력한다. 새 본문 미작성·부칙 혼입을 표시한다. 폐지안은 규정 전체의 폐지문과 새 부칙을 출력하며 일부개정 대비표를 붙이지 않는다.
5. 전부개정의 선택 수정은 검토한 조문·항에서 정확히 일치하는 문장에만 적용한다. 비선택 본문·장절·별표·서식·원문 공백을 보존하고 저장·보관파일 복원 후 되돌리기를 확인했다. 폐지문·부칙·제목의 구조 변경은 직접 편집한다.
6. 요청서는 사전요건과 본문 1–6항을 입력하고 작성자료로 출력한다. 원본의 예시 체크·날짜·견해·관계기관 의견을 사실처럼 채우지 않는다. 원본 배치에 직접 기입한 파일은 아니며 원본 HWPX를 별도로 제공한다.
7. 제출의견 처리는 실제 접수 유무, 반영 여부·이유·반영 조문, 처리결과 통지, 변경 후 재예고 판단을 기록한다. 기존 예고안은 교체해도 이력에 보관한다. 실제 예고·통지·결재를 앱이 대신 완료하지 않는다.
8. 연결 규정은 최대 8개, 원문당 10만 자다. 정확한 법규명과 조·항·별표·서식의 직접 인용만 연결한다. 번호 이동·대상 삭제·본문 변경·전부개정·폐지 후보를 구분한다. 무명 인용과 약칭·간접 영향은 완전 검색 범위에 포함하지 않는다.
9. RAG는 입력 본문 전체 12,000자에서 쟁점을 탐지하고 최대 6개·5,500자의 발췌 예산을 배분한다. 쟁점별 근거 미발견·예산 제외와 입력 조문을 보관한다. 인용 일치는 법적 적용의 타당성을 증명하지 않는다.

## 배포 확인

운영 반영과 실제 화면 확인은 로컬 검사 이후 진행한다. 이 절은 실제 확인 결과만 기록하도록 배포 후 갱신한다.

## 남은 검증과 지원 한계

한컴 한글의 실제 열기·편집·재저장·인쇄, 모바일 실기기·스크린리더, 법제 전문가의 독립 사례 평가와 주무관의 시간 절감 실증은 수행하지 않았다. DOCX·HWPX의 파일 구조 및 내용 검사를 화면·인쇄 품질 검증으로 대신하지 않는다.

요청서의 공식 항목은 연결됐지만 원본 HWPX 체크칸에 직접 기입한 형식은 제공하지 않는다. 별표·서식은 텍스트 중심이며 병합 셀·그림·도형의 구조 편집은 지원하지 않는다. 공포 후 시행 전인 복수 개정법의 복잡한 적용 관계를 자동 확정하지 않는다.
